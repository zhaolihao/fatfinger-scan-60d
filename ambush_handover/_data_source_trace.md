# 成交明细数据源溯源报告（选项 C）

> 目标：定位 viewer 里"明明显示未触发、却有开仓平仓点位"那批成交明细的**真实数据源**，判断它和 viewer 加载的 K 线是否同一份、是否存在时区/口径错位。

## 一、结论先行（3 句话）

1. **两份数据的原始源头是同一份 `ticks/AKEUSDT_2026-09-0X.csv`（逐笔成交 aggTrades）**，不存在第二套数据、也不存在时区错位。
2. 之前说的"21:44 vs 05:44"**是上一轮把 UTC 毫秒误读成 UTC 时刻**造成的假象——回测器自身已用 `TZ=UTC+8` 转成北京时，成交明细里的 `北京时间` 列就是 `09-03 05:44:39`，与 viewer 同一口径。
3. **真正原因不是数据源问题，而是 viewer 的"触发"标注用的是简化锚价模型（computeBase），与回测器真实的锚价逻辑（冻结 + 60s 跟随闸门）不一致**，导致 viewer 算出的墙比回测真实墙高出 4.5%，从而把本应"触发"判成了"未触发"。

## 二、数据来源血缘图（同一根）

```
ticks/AKEUSDT_2026-09-0X.csv   （逐笔 aggTrades: agg_trade_id,price,quantity,transact_time[UTC毫秒],is_buyer_maker）
        │
        ├─① _four_logic_sim.py  (load_bars: 逐笔→1s OHLC, 内部回测)
        │        │  TZ=UTC+8 转北京时
        │        └─► 成交明细_回测.csv   （脚本,版本,币种,腿,方向,类型,北京时间,UTC毫秒,价格,净值U,出场方式）
        │                 ★ 这就是 viewer 里那些"开仓/平仓点位"的来源（fetches 成交明细_回测.csv）
        │
        └─② _agg_1s_kline.py    (逐笔→1s OHLC, 存盘供 viewer 画线)
                 │  TZ=UTC+8 双列(北京时间 + UTC毫秒)
                 └─► K线1s_AKEUSDT.csv  （viewer 加载画 K 线的文件）
```

**关键事实**：①和②读取的是**完全相同**的 `ticks/` 文件，且聚合逻辑一致（开=该秒首笔价、高=最大、低=最小、收=末笔价）。所以 viewer 画的 K 线和回测器内部用的 K 线**逐根一致**，没有数据错位。

## 三、为什么 viewer 显示"未触发"却有成交——数值铁证

以争议秒 **AKE 09-03 05:44:39** 为例（viewer 显示"未触发"，但成交明细_回测.csv 第 50 行有 `S SHORT 开仓`，成交价 `0.040793445`）：

| 项目 | 数值 | 说明 |
|------|------|------|
| 该秒 K 线（来自 K线1s） | O=0.03868 H=**0.041807** L=0.038196 C=0.03956 | 真实行情 |
| **viewer 简化锚价** base_UP | 0.038760 | computeBase：每根 2% 跟随、无冻结/无60s闸门 |
| viewer 上墙 trig = base×1.10 | **0.042636** | 墙被抬到此处 |
| viewer 判定 | H 0.041807 < 0.042636 → **未触发** | ❌ 与成交矛盾 |
| | | |
| **回测器真实锚价** base_UP | **0.037085** | 由成交反推：0.040793445 ÷ 1.10 |
| 回测真实上墙 trig | **0.040793** | 墙在此处 |
| 回测判定 | H 0.041807 ≥ 0.040793 → **触发 ✓** | ✅ 与成交一致 |

**根因一句话**：viewer 的 `computeBase()` 在剧烈波动段把锚价"跟着收盘价一路往上抬"（05:44:39 算到 0.03876），比回测器被**冻结+60s闸门**锁住的锚价（0.037085）高了 **4.5%**，于是墙被抬到 0.0426，把本该穿墙的 0.0418 高点挡在了墙外 → 显示"未触发"，但回测器用锁定的低锚价（墙 0.0408）早已成交。

viewer `computeBase()`（kline_viewer.html:359-371）缺的三样东西，正是回测器 `run_conditional`（_four_logic_sim.py:201-284）里有的：

| 回测器有 | viewer computeBase 缺 | 后果 |
|----------|----------------------|------|
| `frozen` 守卫：持仓期间锚价**锁死不跟随** | 永远跟随 | 波动段锚价被推高 → 墙偏高 |
| `follow_sec` 闸门：≥60s 才允许重挂（旧版） | 每根都判 | 锚价刷新太快 |
| `gate` 8% 跳变过滤 | 无 | 极端跳变也照跟 |

## 四、下一步建议（选项 A 才是真修复）

既然已确认"数据源一致"，问题就**只**在 viewer 的标注模型。要让 viewer 的墙位/触发标注和成交点**永远对齐**，正确做法不是再去凑公式，而是：

> **让回测器导出"逐秒真实锚价轨迹"（`锚价轨迹_回测.csv`：每根 base_UP/trig_UP/base_DN/trig_DN/frozen），viewer 直接加载它来画墙和判定触发**——这样 viewer 用的就是回测器算出的同一个数，零偏差。

这就是之前提的**选项 A**的完整形态。它比"在 viewer 里重写一遍 frozen/60s 逻辑"更稳，因为逻辑只存在于回测器一处，不会两份漂移。

**要我现在就做 A 吗？** 涉及改动 `kline_viewer.html` + 在 `_four_logic_sim.py` 加一段导出，属于代码改动，按规矩先跟你确认再动手。
