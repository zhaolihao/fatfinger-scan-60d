# 复盘：2026-10-04 AT路径完全失效问题

## 问题描述

实盘脚本从AT路径上线以来（约2026-10月初），**从未触发过任何一笔交易**，即使市场出现多次>=6%插针（如TAKEUSDT 12:14振幅10.7%、AINUSDT 12:04振幅12.9%）。

## 排查过程

### 第一阶段：推测锚价窗口问题

**初始假设**：400ms窗口让偏离计算更保守，低频币price_hist积累不到400ms历史。

**"验证"**：
- 拉取TAKEUSDT插针前5分钟的逐笔数据
- 发现平均推送间隔1000ms，最大间隔17723ms
- 计算得出"92%时刻取不到>=400ms锚价"
- 结论：400ms窗口在低频币上失效

**行动**：把400ms改回100ms（实际是80ms取值，PRICE_HIST_MS=300ms）

### 第二阶段：发现AT心跳为0

**关键诊断**：在aggTrade回调函数里加计数器，每1000条打一次`[AT心跳]`日志。

**结果**：启动后3分钟，39个币，AT心跳0条。

**新发现**：不是低频币的问题，而是**aggTrade回调根本没有执行**。

### 第三阶段：发现WS消息格式问题

**进一步诊断**：在`async for msg in ws`循环里加`_RAW_CNT`计数器，每10000条打一次`[AT原始]`日志。

**结果**：启动后3分钟，所有分组AT原始日志0条。

**结论**：`async for msg in ws`完全没收到消息。

### 第四阶段：发现URL编码问题

**根因定位**：
```python
# 第783行（修复前）
uri = f"{FSTREAM_WS}/stream?streams={quote(streams, safe='')}"
```

`quote()`把`@`编码成`%40`，URI变成：
```
wss://fstream.binance.com/stream?streams=takeusdt%40aggTrade
```

Binance WS服务器握手能通过（日志显示"已连接"），但不推送任何数据。

**修复**：
```python
# 第783行（修复后）
uri = f"{FSTREAM_WS}/stream?streams={streams}"  # 不quote()，@保持原样
```

### 第五阶段：修复后仍然无数据

**意外发现**：修复URL编码后，重启脚本，AT心跳仍然为0。

**进一步测试**：
- 直接用Python测试Binance WS的aggTrade流
- 单流格式`wss://fstream.binance.com/ws/btcusdt@aggTrade`也超时
- bookTicker也显示"已连接"但无数据推送
- REST API正常（能拉取BTC价格）

**结论**：Binance WS在这个环境下完全无法推送数据，不是URL格式问题，可能是：
1. 网络防火墙阻止了WS长连接
2. Binance WS服务器对这个IP有限制
3. websockets库的版本或配置问题

## 根本原因

**AT路径从上线第一天就没有收到过任何aggTrade数据**，原因可能是：
1. URL编码问题（`@`被编码成`%40`）
2. 网络环境限制（WS长连接被防火墙阻止）
3. Binance WS服务器对特定IP的限制

## 经验教训

### 1. 有日志不读，靠推测分析，是浪费时间和损失的根本原因

**错误做法**：
- 看到"已连接"就假设WS正常工作
- 用REST API拉逐笔数据模拟脚本行为
- 根据模拟结果推测脚本的问题

**正确做法**：
- 第一步：在代码里加诊断日志，确认WS回调是否真的在执行
- 第二步：如果回调没执行，检查WS连接和消息接收
- 第三步：根据真实日志分析，不靠推测

### 2. "已连接"不等于"有数据"

Binance WS服务器握手能通过（日志显示"已连接"），但不推送任何数据。这种情况在以下场景会发生：
- URL格式错误（如`@`被编码成`%40`）
- 网络防火墙阻止了WS长连接
- 服务器对特定IP有限制

**必须验证**：连接后是否真的收到消息，不能只看"已连接"日志。

### 3. 推测10次9次都是错的，必须用真实数据验证

本次排查中，我做了多次推测：
- 推测400ms窗口太短 → 错
- 推测低频币数据稀疏 → 错
- 推测price_hist积累不够 → 错

**每次推测都浪费了时间，而且误导了后续分析方向。**

**正确做法**：
- 有日志先看日志
- 没日志先加日志
- 用真实数据验证，不靠推测

### 4. 代码修改前必须输出修改清单，等授权

本次排查中，我在没有充分验证的情况下就修改了代码（把80ms改成400ms），导致引入了新的问题。

**铁律**：
- 修改代码前必须输出【修改清单申请】
- 等用户明确授权后才能动代码
- 每次修改后必须列出"实际改动清单"，和申请清单对比
